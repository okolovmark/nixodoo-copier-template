# Every question copier asks

Defaults in the table; anything you leave empty turns its feature off. See [the README](../README.md#the-choices-that-matter) for the ones worth thinking about.

| Question | Default |
|---|---|
| `project_name` | `odoo-dev-env` |
| `odoo_version` | `20.0` (16.0–20.0) |
| `python_version` | per Odoo version (16→3.10, 17→3.11, 18/19/20→3.12; 20 refuses < 3.12) |
| `postgres_version` | 15 for Odoo ≤17, 17 for 18+ (20 needs ≥ 16) |
| ports (http / gevent / nginx / postgres) | derived from the Odoo major (`16.0` → 1669/1672/16069/16432) |
| `db_name` / `db_user` / `db_password` | `develop` / `odoo` / `odoo` |
| `project_dir_var` (project-root env var; make unique to run two projects on one Odoo version) | `ODOO<major>_PROJECT_DIR` |
| `service_suffix` (systemd unit + nix profile suffix; set e.g. `-19` so a second generated project can coexist on one machine — `odoo-19.service`, own profile `~/.local/state/nix/profiles/<project>`) | empty = classic names + `~/.nix-profile` |
| `use_queue_job` | `false` |
| `queue_job_channels` (asked with `use_queue_job`: `[queue_job] channels` of every odoo.conf the project writes, e.g. `root:3,root.ai_help:2`) | `root:3` |
| `editor` | `none` (or `vscode` → settings generator; `odools.toml` ships with `use_claude_code`) |
| `default_repo_pattern` | `https://github.com/OCA/{}.git` |
| `custom_repo_pattern` / `custom_repo_name` | empty → no custom addons repo |
| `use_claude_code` | `true` — CLAUDE.md, hooks, skills, agents, MCP config |
| `module_prefix` / `ticket_prefix` | first word of project name / `TASK` |
| `status_mcp` | `none` (or `teams` → my-status + teams-message skills + bootstrap questions; Teams write goes through the claude.ai Microsoft 365 connector) |
| `tickets_mcp` | `none` (or `odoo` → odoo-tickets skill, ticket links, `ODOO_*_PROD` in `.env`) |
| `odoo_prod_url` | asked when `tickets_mcp=odoo` |
| `task_keys` (prod Odoo runs OCA project_key: every task has a `key` like PROJ-123; `task_key_route` is asked only then) | `false` → a task's reference is `<ticket_prefix>-<id>`, looked up by its record id |
| `task_ai_driven` (prod Odoo runs `project_ai_driven` from okolovmark/nixodoo-addons, which `addons.yaml` pulls on 16.0 and 20.0, its only branches; another version needs its own port: `project.task` fields `task_type`, `tshirt_estimate`, `priority_level`, `solution`, `resolution`, `pull_request_ids`, models `project.task.question`, `project.task.testcase`, `project.task.checklist.item`, `project.task.session` and `project.pull.request`; a pull request is then a record: the pipeline writes its link to the task when it opens the pull request, the deploy stamps the record merged and deployed, a task without a pull request closes with a resolution, and `task_pr_uri` changes nothing; `tshirt_estimate` (Size) is computed from the hours, `task_type` has no default, and a project flagged AI-driven can mark stages a task enters only with a `task_type` and hours above zero; a test case's result is its `state` (`not_run`, `passed`, `failed`, `waiting`, `not_applicable`) with who verified it, when and how, which needs `project_ai_driven` 16.0.2.5.0 or later; the checklist is `project.task.checklist.item` (task field `checklist_item_ids`), which needs 16.0.2.6.0 or later; clarifying questions are `project.task.question` rows (task field `question_ids`), which need 16.0.2.7.0 or later; an internal note opening with a bold category carries it in `mail.message` `note_category`, which needs 16.0.2.8.0 or later; the installed modules a task touches are its `module_ids`, filled from its pull requests' files on tasks of the one project flagged `develops_this_odoo`, which need 16.0.2.10.0 or later; the agent sessions that worked on a task are `project.task.session` rows (task field `session_ids`), which need 16.0.2.12.0 or later; pasted images of task texts become attachments of the task with 16.0.2.13.0 or later; the task's Markdown brief (`project.task` `brief`, one read) needs 16.0.2.14.0 or later; 16.0.2.15.0 or later has no test case `passed` flag and refuses the old state values: on the 20.0 branch the test case results, the checklist item, the question rows and `note_category` need 20.0.2.8.1 or later; `module_ids`, `session_ids`, the images, the brief and the removal of the passed flag come with its port) | `false` → the ticket skills never read them; clarifying Q&A, the technical solution and test cases go to internal notes; no checklist; pull requests as `task_pr_uri` says |
| `use_team_dashboard` (the Team Dashboard: `addons.yaml` pulls `project_team_dashboard` from okolovmark/nixodoo-addons, on top of `project_ai_driven` and `hr_timesheet`; asked with `task_ai_driven` on 16.0 only until its 20.0 port: Project > Team Dashboard by project, manager or department, a multi-project Gantt chart with sub-tasks, dependency lags, baselines and an Excel export, Project > Backlog, the In Progress / Backlog stage flags; it declares `planned_date_start` / `planned_date_end` under OCA project_timeline's names without needing it, rolls them up from sub-tasks (`is_planned_from_subtasks`), and in a project flagged AI-driven the Deadline follows the planned end; `task_timeline` is then yes and not asked, and `addons.yaml` also lists the glue `project_team_dashboard_timeline`, which installs itself where OCA project_timeline is installed too) | `false` → the ticket skills read `is_planned_from_subtasks` only where `fields_get` lists it |
| `use_support_request` (the header Support item: `addons.yaml` pulls `project_support_request` from okolovmark/nixodoo-addons, on top of `project_ai_driven`; asked with `task_ai_driven` on 16.0 only until its 20.0 port: every internal user files a request, a title and a task type, as a task of the project flagged `develops_this_odoo`, as its UAT user, unassigned and unestimated, and lists their open ones; that project's first unfolded stage stays out of its Stages Requiring a Type and an Estimate) | `false` → no Support item |
| `use_timesheet_systray` (the header Timelog timer: `addons.yaml` pulls `project_timesheet_systray` from okolovmark/nixodoo-addons and OCA `project_timesheet_time_control` from the OCA `project` repo; asked with `task_ai_driven` on 16.0 only; a project that already lists the `project` repo keeps one entry and adds the module to it) | `false` → no Timelog item |
| `task_timeline` (prod Odoo runs OCA project_timeline: `planned_date_start` / `planned_date_end`; not asked with `use_team_dashboard`, which declares both: yes then, whether project_timeline runs or not) | `false` → a task is scheduled by `date_deadline` alone |
| `task_pr_uri` (prod Odoo runs OCA project_task_pull_request: `pr_uri`, a text field required before the done stage; with `task_ai_driven` this answer changes nothing: pull requests are records there, and `pr_uri` takes a pull request link only) | `false` → a task closes by its stage move; the PR link goes to a `Progress` note |
| `use_pipeline` | `true` (asked when a custom addons repo is set) |
| `extra_ticket_prefixes` (more ticket prefixes the pipeline takes as task keys, e.g. a second project's) | empty → `ticket_prefix` alone |
| `use_release_notes` (release notes in Odoo: `addons.yaml` pulls the `release_notes` engine from okolovmark/nixodoo-addons, and the project keeps its notes in a holder module `<module_prefix>_release_notes` of its own addons repo; a `release.note` is loaded unpublished from the `notes/<key>.html` file a PR adds; adds the `release-note` skill; asked with the pipeline and Odoo tickets, on 16.0 and 20.0 only, the engine's branches) | `false` → no `release-note` skill, no pipeline Phase 4b, no deploy Step 7.5, and a note file counts as a code change to pipeline-gates |
| `use_kb` | `false` — SessionStart hook: `kb index` + `kb today` into every session (needs `kb` from okolovmark/kb; silent when absent) |
| `backup_s3_bucket` | empty → no backup tooling |
| `prod_ssh_host` (+user/url; `prod_local_ssh_host` adds a `prod-local` alias for the office-LAN address), `test_ssh_hosts` (YAML mapping alias → host, +user/port/url pattern with `{alias}`) | empty → no SSH helpers |
| `prod_remote_project_dir` / `prod_remote_odoo_conf` / `prod_db_name` / `prod_link_addons_cmd` (where this same project sits on the box, for the deploy and prod-ops skills) | `~/<project_name>` / `<that dir>/odoo.conf` / `odoo` / `nix run .#update-repos` |
